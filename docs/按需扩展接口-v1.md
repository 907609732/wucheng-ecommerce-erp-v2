# 按需扩展与发布接口 v1

## 安装结构

启动台使用原应用 ID `com.wucheng.ecommerce.erp.v2`，界面配置位于原用户目录的 `launcher/`。它不初始化业务账本。模块代码位于 `modules/packages/<id>/<version>-<transaction>/`，模块状态位于 `modules/installed.json`。

业务账本独立存放：新采购、销售、总览使用 `module-data/<id>/`；已有账本沿用服务注册表中的实际目录。云仓沿用原用户目录，导出台继续使用“买家订单导出台”目录。卸载仅清理托管代码，保留数据注册信息。

## 官方包清单

`catalog.json` 使用 `lingtu-catalog/v1` 信封：`keyId`、Base64 `payload` 和 Ed25519 `signature`。签名校验对象为 payload 的原始字节。公钥随启动台分发，私钥不进入源码、安装包或扩展包。

payload 的 `schemaVersion` 为 1，`packages` 包含：

| 字段 | 含义 |
| --- | --- |
| id / version | 官方模块标识与 SemVer 版本 |
| hostRange / platform / arch | 启动台版本约束、系统和架构 |
| kind / entry | service、electron、runtime 及包内相对入口 |
| dependencies | 依赖模块标识和版本范围 |
| archive / url | ZIP 文件名及固定官方仓库下载地址 |
| bytes / unpackedBytes / sha256 | 下载大小、解压上限和内容摘要 |

模块 ID 为 warehouse、purchase、sales、overview、exporter、node-runtime、browser-runtime。入口和 ZIP 文件路径拒绝跨目录、Windows 设备路径、替代数据流、链接、加密项和重复文件。

## 安装与生命周期

`ModuleManager` 提供 `list`、`plan`、`install`、`cancel`、`uninstall`、`inspectOffline`、`installOffline`。同一模块重复请求复用一个任务；不同任务在本机文件锁下串行激活。目录刷新不会改变已确认任务的包版本。

安装顺序：验证清单 → 下载或读取离线文件 → 核对大小及 SHA-256 → 受限解压 → 检查闲置 → 停止旧服务并备份 → 维护模式启动 → 服务身份和账本完整性检查 → 持久化新版本 → 开放业务写入。

`transaction.json` 记录未完成激活。发现候选服务已经开放编辑时，恢复流程拒绝自动覆盖账本。恢复失败保留事务、原件和候选数据，不能当成安装成功。旧版本不能直接降级使用新数据库。

## 本机接口

业务接口继续使用 `/api/integration/v1`，仅绑定回环地址，修改请求验证来源和授权。增加：

| 接口 | 作用 |
| --- | --- |
| GET /capabilities | 返回身份、版本、实际代码/数据目录、busy、maintenance |
| POST /maintenance/activate | 健康检查成功后解除维护模式；需要本机授权及 confirm |
| POST /open | 打开已激活的 Electron 模块窗口 |
| POST /stop | 任务空闲时停止服务 |

维护模式拒绝普通业务写入。历史订单正式导入仍须完成采购页面的两次确认；CLI/MCP 的草稿接口不能绕过。

启动台 IPC 只接受自己的主框架。内嵌采购、销售页面仅可请求受限导航和数据刷新，不拥有安装或任意文件执行权限。

## 构建与发布

使用 `scripts/build-module-pack.mjs` 从各独立工作区构建。服务模块只复制白名单代码，在临时目录用锁文件安装生产依赖。公开销售包不携带个人店铺预置；采购包不携带个人录入人快捷项。OCR 模型及许可证随采购包提供。

使用 `scripts/sign-module-catalog.mjs` 签署完整目录，并生成包含全部依赖的离线 ZIP。在线和离线安装使用同一校验及生命周期。

启动台由 `scripts/build-launcher.mjs` 单独打包，保留现有 Electron Builder/NSIS 和 electron-updater。不要使用云仓单体的旧构建命令代替纯启动台构建。

模块大文件发布至 GitHub Releases；稳定目录位于 `modules-stable` 的 `catalog.json`，版本文件使用不可混淆的独立发布标签。先上传并验证模块文件，再更新稳定目录和发布启动台。发布签名与 Windows Authenticode 代码签名是不同机制。
