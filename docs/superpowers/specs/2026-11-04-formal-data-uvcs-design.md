# 正式数据 Unity Version Control 托管设计

## 目标与当前环境

用户要求正式数据由 Unity Version Control 托管，每次新业务写入自动提交，生成可读注释，并在软件内查看提交。

当前源码分支 codex/payroll-sheet 有其他任务的未提交修改，本功能实施应使用独立工作区。现有文档规定业务数据不进源码仓库，本次扩展为单独的私有数据仓库，不改变源码仓库的数据排除规则。

## 方案比较与建议

1. **推荐：每次业务保存固定一致性快照，异步提交独立私有仓库。** 满足逐次记录，可生成业务注释，需增加事务事件、快照及可靠队列。
2. 定时合并快照。开销较低，但不能精确对应每次保存，不符合用户原话，除非用户另行选择。
3. 监听文件变化直接提交活动 SQLite。无法准确对应业务操作，也无法可靠覆盖 WAL 数据，不采用。

采用用户选择的“每次业务保存自动提交”方案。正式启用状态以验收记录为准。

## 记录粒度与数据范围

- 一次成功的业务保存一条记录，包括新增、修改、删除及业务配置修改；批量导入整体一条，不按 SQL 行生成提交。
- 无变化、只读请求、预览、验证失败与已回滚事务不生成业务版本。系统迁移产生的数据变化须明确标为系统迁移。
- 首次建立三模块基线，之后每次快照承诺对应模块的一致状态。跨模块交接以关联 ID 展示多个模块记录，不宣称三个独立数据库拥有同一原子事务。
- 上传白名单为三个正式业务账本、恢复业务所需的非秘密配置、正式原件与业务附件，实施时逐类检查；不遍历上传整个数据目录。
- 密钥、登录会话、浏览器授权、运行文件、日志、临时下载和历史备份排除。Gateway 身份库不混入业务快照。
- 整库快照前核查 SQLite 表内是否存有凭据或授权数据；目录白名单不能排除数据库内部秘密。若存在混存，先采用经验证且可恢复的业务数据导出方案或拆分相关存储，禁止直接上传含秘密的整库。
- 仓库建议名：五成ERP正式数据；使用现有 cloud.cn 组织下独立私有仓库。创建前核实仓库权限与可用容量，不启用付费扩容。

## 事务、快照与提交可靠性

1. 每次业务操作建立稳定 eventId，携带模块、操作人、操作类型、业务实体或批次、增改删数量及允许记录的摘要。
2. 在业务事务中写入持久化 outbox，与业务数据共同提交和回滚。复用已有模块修订触发器作变化与漏记检测，覆盖浏览器、采购手机入口、后台任务及脚本；不能只在网关成功响应后监听。
   脚本覆盖限于接入统一写入协议的受支持脚本；任意外部 SQL 写入不受进程内屏障保护，检测后报告版本保护异常，不承诺可还原未受控写入的每个中间状态。
3. 在业务 COMMIT 前同步固定该事务所见的白名单业务表、恢复 schema 和附件快照，再将事件写入同一事务。后台只上传固定快照，不读取随后已变化的活动库补造旧版本。
4. 本地快照失败则业务事务回滚，不显示已保存。启动时检查未被正确处理的变化记录并拒绝静默继续；不能补造缺失的精确历史。业务逻辑导出排除整库中混存的授权、会话和其他运行数据。
5. 上传独立队列由单个写者串行执行官方 cm 命令。保存事件 ID、快照摘要、队列状态、尝试次数、下次重试时间及远端 changeset ID。网络故障只延后上传，不要求重复保存业务。
6. 每次提交更新仓库固定模块快照路径及事件元信息，借助 UVCS 历史保留版本，避免每次永久新增一份完整目录。默认每模块保留最近10个已提交本地快照，释放更早的已确认快照；待提交与失败快照不清理，共享附件 blob 暂不回收。
7. 远端成功而本地状态未更新时，按注释中的稳定 eventId 查询远端去重，再更新本地状态，避免断电后重复提交。
8. 注释模板：`采购｜批量导入｜新增23条、修改2条｜操作人：成员名称｜事件：唯一标识`。提交身份与业务操作人分开记录；不将完整买家资料、税号、密码等写进注释。
9. 本地磁盘不足时明确告警并停止继续接受无法保护的业务写入，不丢弃待提交队列。

现有 server/backup.mjs 要求停模块，只供现有维护备份使用，不能直接改成每次保存调用。

## 服务身份与托管

先核实组织支持的自动化登录方式，优先选择具备目标私有仓库最小必要权限的运行身份。不能将当前用户 whoami 成功当作 LocalSystem 已登录；不直接复制私有凭据文件。

若沿用用户会话内提交代理，应明确退出登录后等待重试的限制；若配置独立服务身份，应在实际运行身份下完成只读查询和合成数据提交验证，才能标记为已接入。不得在源码、提交注释或页面中保存凭据。

## 软件交互与界面

- 现有顶部导航增加“数据版本”，保留连接状态含义；单独显示“待托管 N／托管异常 N”。
- 保存提示区分“业务已保存，等待托管”和“已托管”，只有远端确认后显示真实 cs 号。
- 列表支持时间、模块、操作人、状态筛选，展示中文业务摘要、发生时间、操作人、状态和提交号。
- 右侧详情显示业务动作摘要、增改删数量、附件清单、事件 ID、校验摘要及远端提交时间；首版不展示数据库整行或字段级前后对照。摘要不冒充文件内容差异。
- 失败说明“不必重复保存业务”，提供“重试托管”，后台自动重试。
- 沿用 ui/tokens.css 的字体、间距、38px 控件和现有顶部导航；绿色已托管、橙色等待、红色失败，均同时显示文字。窄屏改为卡片与全宽详情。
- 遵循当前已认证公司成员的现有权限约定，不自行新增管理员专属历史权限。凭据维护放主机运维流程。
- 首版不提供一键覆盖正式账本的恢复操作。历史版本先支持查询和查看元信息；恢复到隔离目录的演练作为验收，正式恢复另行明确范围。

## 验收与接入顺序

1. 独立工作区与合成数据实施，保护现有未提交工资界面工作。
2. 验证连续两次保存对应两个准确状态、批量导入一条、回滚不生成版本、无变化不提交、手机与后台写入覆盖、附件与变更摘要正确。
3. 验证断网与重启补交、事务后快照前崩溃检测、远端成功后本地未记账去重、快照失败与磁盘不足的阻止写入行为。
4. 实际后台运行身份对专用私有仓库完成合成数据提交，核对注释、cs 号和页面展示，并从远端恢复到独立目录核对账本与附件摘要。
5. 使用正式数据副本验证性能、白名单和恢复一致性。记录保存耗时，不能将全量重复上传造成的长延迟隐藏在“异步”字样下。
6. 程序代码走 GitHub 检查，业务数据不上传 GitHub。正式切换前保留一致性备份与回退版本，在维护窗口建立正式基线并启用；逐项记录本地验证、云端提交和正式接入结果。
