# 运行维护

当前正式环境为飞牛应用中心安装的 **五成ERP 0.15.5**，日常从飞牛桌面打开。Windows 旧服务和 ERP Docker 容器不再作为正式入口或回退服务。程序、运行文件、账本及备份分开存放。

## 当前环境

- 正式应用 ID：`wuchengerp`；安装卷为存储空间 4。
- 程序：`/vol4/@appcenter/wuchengerp/erp`；运行文件和日志：`/vol4/@appdata/wuchengerp/runtime`。
- 正式账本、附件、身份、月锁及原 UVCS 工作区：`/vol4/@wuchengerp-data/erp`。
- 升级停写备份：`/vol4/@wuchengerp-data/backups/before-upgrade-*`。完整迁移备份继续保留在原备份卷，不清理必要回退材料。
- 原生包自带 Node.js 24.22.2、Chromium、Xvfb、noVNC 和三个业务模块；保留宿主 Tailscale 与官方系统 UVCS CLI。
- ERP 正式运行不依赖 Docker。`jx-tunnel`、`qwrt`、`docker-home-assistant` 属于其他业务，禁止顺带停止或删除。
- 云仓和订单导出使用已有独立工作区；其程序、授权及数据不在 ERP 清理范围。

## 用户访问

飞牛「系统设置 → 应用设置 → 五成ERP → 桌面访问」采用 **设备内所有用户**。原生包使用 `fnos.accessPolicy=fnos`，不再维护额外 UID 名单；旧配置中的 `allowedUids` 仅留作兼容，不参与该策略的准入判断。入口仍校验飞牛可信 Unix 代理、来源和会话，业务复核、密码及月锁保护继续生效。

已通过普通飞牛账号登录和三个业务页面验收。部分中文账户显示名存在编码问题，身份与准入按飞牛 UID 核对，不能以显示名乱码判断登录失败。

## 更新流程

1. 在源码工作区修改、检查并推送，使用 GitHub 的 `fnos-native.yml` 工作流执行完整测试及隔离包构建：`check_scope=full`、`build_trial=true`。
2. 保留同一提交、同一次构建的正式 FPK、隔离 FPK、对应源码伴随包和校验文件。核对 `BUILD-INFO.txt`、SHA256 及实际运行报告，不能混用候选包。
3. 在独立 `wuchengerptrial` 中验收普通账号访问、真实页面和正常停启。验收后停用试装版，再操作正式版，避免两个实例及大文件校验同时争用 NAS 资源。
4. 从应用中心上传正式 FPK，必须重新核对向导选择 **沿用已安装原生数据**、迁移路径为空、沿用已安装系统 CLI。飞牛可能带回旧的「迁移」答案，不能直接沿用。
5. 原升级钩子先停写，生成完整备份并在副本中校验恢复，通过后才替换程序。失败时保留原数据及备份，查明原因；不得改成新建空账本、关闭 UVCS 或绕过校验。
6. 核对程序版本、原 serverId/dataSetId/fnOS 实例、三个账本、数据版本托管状态，以及管理员和普通账号的真实页面。验收完成后移除试装应用、临时诊断项目和临时目录。
7. 大附件可由 `ci.yml` 的手动归档任务直接送入已有发布草稿：传入已成功的 `promote_run_id`、精确 `promote_sha` 和 `promote_tag`。它只归档并校验五个正式交付文件，不重建、不覆盖、不公开发布。实机验收通过后再发布草稿，必须同时提供匹配的 FPK 和完整对应源码。

## 故障与回退

先查 `/var/log/apps/wuchengerp.log` 和运行目录中的 `logs/native-supervisor.log`，保留最早的底层错误。源账本只读检查可能需要已有 WAL/SHM；恢复检查应复用既有副本校验方式，不在正式源目录创建临时文件或通过忽略 WAL 得出结论。

旧版 Chromium 关闭前挂接页面超时可能留下 Singleton 锁；0.15.5 通过本代唯一调试地址发送正常关闭指令。启动失败后的异常清理仍需核对实际进程、端口与锁，不能只看 supervisor 记录消失便删除目录项。清理须持有生命周期和实例互斥，逐项确认 UID、设备号、inode、目标及失效状态；禁止宽泛杀进程、递归删除正式目录或全局 Docker prune。

回退使用已验证的原生 FPK 与兼容账本，不依赖已删除的旧 Docker ERP。正式版产生新业务写入后，禁止直接用旧备份覆盖当前账本。卸载只移除程序，账本与备份默认保留；删除数据必须另有明确的数据清理范围。
